## 二、架构

### 2.1 目录结构

```
Godot-Mir2/
├── project.godot
├── docs/
│   ├── protocol.md            # 阶段 0 产出，脚本生成
│   ├── map-format.md          # 地图格式，已验证
│   └── plan.md                # 本文件
├── scripts/
│   ├── net/
│   │   ├── mir_framer.gd      # 帧编解码（LEB128 / XOR / 4 种消息体）
│   │   ├── mir_proto.gd       # 消息表 + 结构体读写基元
│   │   └── mir_client.gd      # 连接、心跳、请求应答配对
│   ├── data/
│   │   ├── map_loader.gd      # .bin 解析
│   │   ├── map_view.gd        # 视野裁剪 + 瓦片池化
│   │   └── tex_cache.gd       # PNG 运行时加载与 LRU
│   ├── actor/
│   │   ├── actor.gd           # 基础实体
│   │   ├── player.gd          # 主角，8 方向移动
│   │   └── action_fsm.gd      # ActionType 状态机
│   └── ui/
│       ├── login.gd
│       ├── hud.gd
│       └── chat.gd
├── scenes/
├── tools/
│   └── gen_protocol_doc.py    # 从 C++ 头生成协议文档
└── .gitignore                 # 忽略 .godot/ 与素材
```

### 2.2 分层与数据流

```
[网络层] mir_framer  →  帧解码  →  mir_client  →  信号
                                                    ↓
[数据层] map_loader / tex_cache  ←────────────  scene 层
                                                    ↓
[表现层] actor / ui  ←── 订阅信号 ──┘
```

**原则**：`scripts/net/` 不认识任何节点；`scripts/actor/` 不认识 socket。跨层只用信号。

### 2.3 Autoload 划分（难以回退，先定）

| 名称 | 职责 | 为什么是全局 |
|---|---|---|
| `Net` | 唯一的 TCP 连接 + 帧编解码 | 全局单连接，生命周期跨越所有场景 |
| `TexCache` | PNG 加载与 LRU 缓存 | 跨地图复用，重复加载代价高（0.86 ms/张） |
| `Game` | 玩家状态、当前地图、UID 映射 | 跨场景共享 |

## 三、阶段划分与验收标准

### 阶段 0：协议与格式摸底 ✅ **已完成**

**产出**
- `docs/protocol.md`：87 CM + 115 SM 全量表，含帧格式、LEB128、XOR 压缩、cerealf 封装
- `docs/map-format.md`：地图 .bin 字节布局，**实测验证**
- `tools/gen_protocol_doc.py`：可复现生成

**验收证据**
| 项 | 结果 |
|---|---|
| CM/SM 条数 | 87 / 115，注册表**零缺失** |
| 结构体 sizeof | 用 ucrt64 g++ 实际编译测量，非手算 |
| 地图解析 | `1 + 24 + 160000×260 = 41,600,025` 字节**精确吻合** |
| texID 映射 | 解出 `0x0102F2` → 对应 `000102F2.PNG` 存在 |

---

### 阶段 1：协议层客户端（无服务端也能自验）

**目标**：能独立编码/解码每一种 P0 消息，不依赖服务端。

| 任务 | 验收标准 |
|---|---|
| 帧编解码器 | 往返测试：编码→解码→字段一致，覆盖 4 种消息体 × 有无 respID |
| 结构体读写 | `ActionNode` 28B、`CMLogin` 136B、`SMOnlineOK` 177B 与 C++ 实测值一致 |
| cerealf 解码 | 能解 zstd / XOR / 不压缩三种标记的 type-3 消息 |
| **离线回放** | 抓一份真实服务端字节流，本地解出可读字段 |

> **卡点**：需要真实字节流做回归。若服务端不可用，则用 C++ 侧导出的样本文件。

---

### 阶段 2：单张地图渲染（**你要的"先做一张地图"**）

**目标**：进游戏看到「比奇县_0」地图，能点击走路，视角跟随。

| 任务 | 验收标准 |
|---|---|
| `map_loader.gd` | 解析 `0.bin` → 800×800 格，texID 与 Python 参考实现逐格比对一致 |
| 瓦片渲染 | 视野内瓦片正确绘制，无错位；**同屏瓦片数 ≤ 1,600** |
| 纹理池 | 实测帧率 ≥ 60 fps（RTX 机器上），切图不卡 |
| 点击走路 | 点击目标格，A* 寻路（`common/src/pathf.cpp` 逻辑移植），主角逐格移动 |
| 8 方向 | 方向编号与 `dir8_t` 一致（1=上…8=左上） |

**性能预算**（基于实测 0.86 ms/张）

| 项 | 预算 | 依据 |
|---|---|---|
| 同屏瓦片 | 60×40 = 2,400 格上限 | `SYS_MAPVISIBLEW/H` |
| 首屏加载 | ≤ 800 ms = 2,400 × 0.86 ms 全量；**必须异步+池化** | 实测 |
| 纹理缓存 | LRU 上限 4,096 张 ≈ 4,096 × 96×64×4 B = 96 MB | 实测尺寸 |

---

### 阶段 3：联机验证（**依赖服务端**）

**目标**：Godot 客户端 ↔ 真实服务端跑通 登录→进图→移动→攻击→聊天。

| 任务 | 验收标准 |
|---|---|
| 登录握手 | `CM_PING`→`SM_PING` 往返 tick 一致；`CM_LOGIN`→`SM_LOGINOK` |
| 选人进图 | `CM_QUERYCHAR`→`SM_QUERYCHAROK`；`CM_ONLINE`→`SM_ONLINEOK`→`SM_STARTGAMESCENE` |
| 视野同步 | 收到 `SM_CORECORD` 生成实体；`SM_ACTION` 驱动移动动画 |
| 移动 | 客户端发 `CM_ACTION`(ACTION_MOVE)，服务端回 `SM_ACTION` 全员同步 |
| 攻击 | `CM_ACTION`(ACTION_ATTACK) → `SM_ACTION` + `SM_HEALTH` 扣血 |
| 聊天 | `CM_PLAYERSAY` → `SM_PLAYERSAY` 广播 |

> **强依赖 `Q1`**：没有服务端就无法验收。**这是唯一无法本地闭环的阶段。**

## 四、排期

以「每个阶段可独立验收」为切分，不做虚假的时间承诺。**实际耗时取决于你的可用时间**，这里给的是**顺序与依赖关系**。

| 阶段 | 内容 | 前置依赖 | 可独立验收 |
|---|---|---|---|
| 0 | 协议 + 地图格式摸底 | 无 | ✅ **已完成** |
| 1 | 帧编解码 + 结构体读写 | 0 | ✅ 纯本地可验 |
| 2 | 单张地图渲染 + 点击走路 | 1（复用 UID/坐标常量） | ✅ 纯本地可验 |
| 3 | 联机联调 | 1 + **服务端** | ❌ 需服务端 |
| 4 | 系统扩展 | 3 | ❌ 需服务端 |

**并行建议**：阶段 1 与阶段 2 的数据层可并行（互不依赖）。
