## 0. 结论摘要

本项目采用 **按子系统批量迁移、尽量保留原逻辑结构、最后集中做完整行为验证** 的路线，管理后台改为 Web。

同时建议区分两件事：

1. **完整玩法测试后置**：不在每个功能点旁边做完整玩法验收，避免把复刻工程变成长期边写边测项目；
2. **低成本自动化门禁不能后置**：每个批次至少保证能够编译、静态检查通过、核心协议样本可编解码、数据库可打开、Lua 脚本可加载。

不建议在全部代码完成前完全不编译、不验证。这样最终大概率会得到一个无法启动、也无法定位问题来源的大型集成体。批量迁移是效率选择，批次门禁是可控性底线。

## 1. 项目目标

### 1.1 总目标

使用 Go 重写 `mir2x` 服务端，并满足以下默认兼容目标：

- 现有 C++ 客户端能够连接，不要求客户端改协议；
- 继续使用现有 SQLite 数据库、脚本和资源格式；
- 尽可能保持地图、战斗、物品、NPC、任务、行会、交易等行为一致；
- 使用 Web 管理后台替代原 FLTK 管理界面；
- 最终产物优先采用少量可执行文件和明确的资源目录进行部署。

### 1.2 兼容级别

建议按以下级别验收：

| 级别 | 内容 | 要求 |
|---|---|---|
| L0 | 工程可构建 | `go build ./...`、`go vet ./...`、`gofmt` 通过 |
| L1 | 协议兼容 | 字节级编解码与 C++ 样本一致 |
| L2 | 数据兼容 | 能读取、写回现有 SQLite 数据和二进制字段 |
| L3 | 脚本兼容 | 原 Lua 脚本无需业务性改写即可加载运行 |
| L4 | 玩法兼容 | 客户端关键流程和 C++ 服务端结果一致 |
| L5 | 运维兼容 | 重启恢复、Web 管理、日志、指标、压力测试通过 |

### 1.3 非目标

首版不包含：

- 复刻 FLTK 桌面管理窗口；
- 用 HTTP/JSON 替换游戏客户端 TCP 协议；
- 大规模重写现有 Lua 业务脚本；
- 重新制作客户端资源或地图资源；
- 在第一轮复刻中重做所有游戏平衡性和历史特殊行为。

## 2. 实施策略

### 2.1 批量照搬翻译

迁移以 C++ 源文件和 Lua 脚本为基准，按模块批量转换为 Go：

- 允许保留原文件名语义、函数名语义和关键数据结构；
- C++ 类优先映射为 Go struct + method；
- 继承结构使用组合与接口替代，但不为了Go 风格随意拆分原逻辑；
- 使用 `defer` 对应 RAII，使用 `error` 对应可恢复异常；
- 协议、时间、随机数、整数宽度、对象生命周期必须显式处理；
- 对暂时无法等价实现的分支，必须 `panic` 或返回明确错误，不能静默返回零值；
- 维护 `MIGRATION_MANIFEST.md`，记录C++ 源文件  Go 文件的映射、已迁移状态、已知差异和待办。

### 2.2 批次门禁

每个批次完成后只要求以下自动化检查，不要求完整玩法测试：

- `gofmt -l .` 无输出；
- `go vet ./...` 通过；
- `go build ./...` 通过；
- 协议 golden fixture 编解码通过；
- SQLite 样本库可打开，关键表可读写；
- 全部 Lua 脚本至少可按预期加载并完成一次最小调用；
- 批次报告列出尚未迁移、已知不兼容和风险项。

### 2.3 完整验证后置

所有主要模块落地后，进入集中验证阶段：

- 与 C++ 服务端做协议和行为差分；
- 使用真实客户端执行完整业务链路；
- 使用真实数据库和资源做兼容回归；
- 做竞态检测、长时间运行、重连和重启恢复测试；
- 对 Web 管理后台做认证、授权和审计测试。


### 4.1 并发模型

不建议逐对象照搬 C++ ActorPool 线程实现。建议：

- 网络 I/O 使用 goroutine；
- 每张地图使用一个串行执行队列或单 goroutine 世界循环；
- 玩家、NPC、怪物作为地图内实体，状态变更由所属地图顺序执行；
- 跨地图操作通过消息邮箱排队；
- 数据库操作异步执行，但结果回注时必须重新进入所属执行上下文；
- 世界时钟、定时器、随机数源集中管理；
- 对协议有影响的 32 位 tick 行为单独封装，避免无意改变兼容性。

目标不是追求字面上的 C++ 线程模型一致，而是保持可观察的消息顺序和行为稳定。

## 6. Web 管理后台方案

### 6.1 技术形态

- 后端：Go HTTP 服务，使用 REST/JSON；
- 实时数据：WebSocket 或 SSE；
- 前端：默认 Vue 3 + TypeScript + Vite，构建产物通过 `go:embed` 嵌入服务端；
- 认证：管理员账号与游戏账号分离；
- 密码：Argon2id 或 bcrypt 哈希；
- 权限：按角色划分只读、运维、管理员；
- 默认监听：`127.0.0.1`，生产环境通过反向代理启用 TLS；
- 审计：所有写操作记录操作者、时间、目标、参数和结果；
- 安全：CSRF 防护、登录限流、会话过期、敏感字段脱敏。

### 6.2 页面范围

- Dashboard：进程状态、运行时长、在线数、地图数、内存/goroutine、错误率；
- 玩家：搜索、在线状态、角色信息、踢下线、禁言、传送、公告；
- 世界：地图列表、实体统计、刷新状态、异常地图；
- 数据：账号、角色、背包、行会、拍卖和邮件查询；
- 配置：只读配置展示、白名单热加载、变更审计；
- 日志：实时日志、过滤、下载；
- 运维：重启、维护模式、健康检查、指标导出。

游戏登录协议和 Web 管理协议必须完全分离，不能复用游戏端口，也不能默认使用 `admin/admin` 这类弱凭据。

## 7. 迁移规范

### 7.1 C++ 到 Go 的对应规则

| C++ | Go |
|---|---|
| class | struct + method |
| inheritance | composition/interface |
| RAII | `defer` |
| exception | `error`，不可恢复错误使用 panic |
| template | generic 或具体类型实现 |
| smart pointer | 明确所有权和生命周期 |
| mutex + actor | 串行所有权队列，避免跨实体加锁 |
| C++ `int` | 根据协议使用 `int32`/`int64` |
| C++ `unordered_map` | map，但不得依赖遍历顺序 |
| printf 日志 | 结构化日志 |

### 7.2 禁止事项

- 禁止用 JSON/`encoding/gob` 替换旧游戏二进制协议；
- 禁止静默吞掉尚未迁移的 C++ 分支；
- 禁止在 Web 请求处理器中直接修改地图实体；
- 禁止依赖 Go map 遍历顺序生成网络消息；
- 禁止把 C++ 的有符号/无符号行为未经检查改成 Go 默认整数；
- 禁止在未记录差异的情况下重写 Lua 业务规则。

### 7.3 批次交付物

每个批次必须提交：

- Go 源码；
- 对应源文件映射和状态；
- 未实现项和已知差异；
- 可通过的批次门禁；
- 必要的 golden fixture；
- 更新后的本方案或迁移清单。

## 8. 风险清单

| 风险 | 等级 | 处理方式 |
|---|---|---|
| 协议序列化不一致 | 高 | 先做字节级 fixture，保留 C++ oracle |
| Lua 5.4/协程语义不兼容 | 高 | 优先兼容原 Lua 5.4；必要时 CGo 嵌入原生运行时 |
| Actor 顺序和并发语义变化 | 高 | 地图串行执行，网络 I/O 与状态逻辑分离 |
| C++ 隐式转换/整数行为差异 | 高 | 明确宽度，关键路径做差分 |
| 批量翻译导致后期集中爆炸 | 高 | 批次编译和 smoke gate，禁止长期不可构建 |
| SQLite BLOB/自定义函数不兼容 | 中高 | 真实数据库回归，固定驱动版本 |
| 现有资源路径和版本漂移 | 中 | 哈希、版本清单、资源独立发布 |
| Web 管理权限过大 | 中 | 默认本地监听、RBAC、审计、只读优先 |
| 无许可证或资源授权不明 | 中 | 发布前确认代码和资源授权 |
| 源工作树存在未提交修改 | 中 | 迁移前冻结 patch 和文件哈希 |

## 9. 验收标准

至少满足以下条件才视为第一版复刻完成：

- Go 服务端可在干净环境启动；
- 现有客户端可完成登录、建角色、进图、移动、战斗、NPC、任务、交易等核心流程；
- 协议消息与 C++ golden 样本一致；
- 现有 SQLite 数据库可读写，且不破坏 C++ 服务端兼容性；
- 原 Lua 脚本无需业务性改写即可加载；
- 重启后角色、任务、物品、社交和经济数据保持一致；
- `go test -race` 无明显数据竞争；
- Web 管理后台具备登录、权限、审计和安全默认值；
- 迁移清单中没有未说明的关键 TODO。

## 10. 待确认决策

6. 脚本和游戏资源是随服务端发行，还是作为独立内容包发布。
